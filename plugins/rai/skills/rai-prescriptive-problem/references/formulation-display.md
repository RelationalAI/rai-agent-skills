## Formulation Display

Before solving, inspect the mathematical formulation:

```python
# Print the full formulation (variables, constraints, objectives)
problem.display()
```

Use `problem.display()` to verify the formulation looks correct before calling `problem.solve()`. Counts (`num_variables()`, `num_constraints()`, `num_min_objectives()`, `num_max_objectives()`) and how to check them: [pre-solve-validation.md](pre-solve-validation.md) > Cardinality checks.

### Display output structure

`problem.display()` prints a structured summary with three sections (shape, not exact text):

```
Problem (numeric type: Float):
• 6 variables (6 cont)
• 1 minimization objective
• 14 constraints

Variables:
    name type  lower  upper
 beef_v  cont    0.0   10.0
 chick_v cont    0.0   10.0

Minimization objectives:
  cost: sum(amt_beef * 3.5, amt_chick * 2.25, amt_rice * 0.5)

Constraints:
  min_calories: sum(amt_beef * 250.0, amt_chick * 300.0, amt_rice * 130.0) >= 1800.0
  cap_1: sum(f_1, f_2) <= 10.0
```

Members are **enumerated**, coefficients arrive as numeric literals, and member names come from
`name=` rather than the property name. An expression over 200 rows prints 200 members, so compare
by content rather than by scanning for a symbolic form the renderer never emits.

**Sections:** Summary block (totals by kind), Variables table (name, type, lower, upper bounds), then Objectives and Constraints printed as `name: expression` (or just `expression` when unnamed). Constraints generated by `.per()` print one row per group. Variable names come from `name=[...]` on `solve_for()`, and from 1.29 `display()` raises `ValueError` unless every variable is named. `display()` checks **every** decision variable in the Problem, not only the ones you read, and it fires once at least one has grounded: on a model with no data it prints `Problem (numeric type: Float): empty` and skips the check. The name must also **discriminate**: `display()` only rejects null names, so a constant `name="x"` gives every instance the same name, and rows whose remaining terms are also identical become indistinguishable — twelve sites all reading `sum(x) <= 5.0` — with no warning. Include the identifier, as in `name=["x", Entity.id]`.

### Diagnosing issues from display output

`<unrendered>` in place of a `display()` row's text means an incomplete engine read, or an argument the renderer cannot consume (the whole expression fails closed rather than rendering partially). It never means a missing install: `display()` installs on demand, and it raises `ValueError` before printing if a variable is unnamed.

The display output is the primary diagnostic tool — it shows the **materialized** formulation (after entity creation, `.where()` filtering, and `.per()` grouping), not just what was declared in code.

**Counts in the summary block:** zero or too few variables, constraints or objectives, and their causes, are covered in [pre-solve-validation.md](pre-solve-validation.md) (§ 1-3 and Cardinality checks). *More* variables than expected usually means an unconstrained cross-product (a missing `.where()` relationship filter) producing all pairs.

**Expression inspection:** Read the symbolic expressions in the Constraints section to verify:
- Aggregation scope (`.per()`) matches intent — e.g., capacity constraint should be `.per(Resource)`, not global
- Join paths connect the right concepts — e.g., `sum(Allocation.x_spend).where(Allocation.channel == Channel)` not `sum(Allocation.x_spend)` globally
- Coefficient signs are correct — e.g., `cost * qty` not `-cost * qty` for a cost minimization

**Pre-solve vs post-solve:** Always inspect `problem.display()` output **before** calling `problem.solve()`. After a failed solve (infeasible, unbounded), compare the display output against the expected components for the problem type: signatures in [SKILL.md](../SKILL.md) > Problem Type Classification and Solver Selection, canonical shapes per family in [problem-patterns-and-validation.md](problem-patterns-and-validation.md) > Common Problem Patterns. A missing component is the likely root cause.

## Counts before display, especially for large problems

For large problems, full `problem.display()` may print thousands of lines and obscure the issue. Engine-side counts are cheap scalar reads against the populated formulation Concepts and prove (or disprove) that the formulation grounded the expected number of variables and constraints. Display only what's worth reading: cap the print with `problem.display(limit=N)`, or drill in with the targeted selects below.

Count code, including the per-constraint check that localizes *which* constraint is short: [pre-solve-validation.md](pre-solve-validation.md) > Cardinality checks.

## Targeted Inspection with `display_string`

*Requires `relationalai>=1.29`.*

Every objective and constraint carries a `display_string` property holding the text rendered from its expression tree. Selecting it returns a DataFrame you can filter, join and count.

Install the rendering rules once per `Problem`, after the model is fully declared, then select. Installing on one Problem does not render another Problem's expressions, even on the same model — call it on each Problem whose expressions you will select:

```python
x_vars = problem.solve_for(Route.x_flow, name=["flow", Route.origin, Route.dest], lower=0)
cap = problem.satisfy(
    model.require(Route.x_flow <= Route.capacity),
    name=["cap", Route.origin, Route.dest],
)

problem.install_display_strings()

# Just the capacity constraints
print(model.select(cap.name, cap.display_string).to_df().to_string(index=False))

# Every constraint on the problem
c = problem.Constraint
print(model.select(c.name, c.display_string).to_df().to_string(index=False))
```

**Print rendered text with `to_string`, not a bare `print(df)`.** pandas clips a cell at 50 characters, so `print(df)` shows a rendered constraint cut off with an ellipsis; `df.to_string(index=False)` prints it whole.

Rendered numbers are backend-dependent: a float literal at or above `1e6` renders differently on LQP than on the SQL backend, which can also move the order of members within a `sum`. Compare rendered text within one backend, never across two.

`display_string` is declared whether or not its rules are installed, so the select always returns a row per expression and a **null** `display_string` is never accompanied by an error. Two causes account for almost every case, and they need different fixes:

- **The rules are not installed.** Only `problem.display()` installs on demand; a direct select does not.
- **A decision variable in the expression was declared without `name=`.** Expressions render server-side from `Variable.name`, so one over an unnamed variable stays null *after* a correct install. Re-installing will not fix it — a second install is a no-op. Name every variable you intend to inspect.

(Rarer causes exist — an incomplete engine read, or an argument the renderer cannot consume, which fails the whole expression closed rather than rendering it partially — so treat these two as the first checks, not the only ones.)

**Filter on `.name`, never on `display_string`.** A direct select keeps a null row and shows you the null; a `where` on the property *drops* it. So a predicate over `display_string` silently removes exactly the unrendered rows you are trying to diagnose, and an uninstalled problem filters down to nothing that looks like "no constraints grounded".

Under Deploy Mode, install before deploying — the rules must exist at deploy time. Installing is idempotent, but not free: on the SQL backend the first query after it renders **every** expression in the problem, whether or not that query selects one, and any later model change re-pays it on the next query.

Three limits decide whether that cost is noticeable. **The figures below were measured offline against in-memory DuckDB.** On Snowflake the same install costs far more and does not obviously scale with the model: the first query after installing has been measured at +131s to +240s, with the next query at most 0.3s.

- **It tracks constraint *declarations*, not expressions.** Twenty-five constraints declared separately cost roughly nine times what the same twenty-five cost when they ground from one declaration, because installing re-plans every block in the model.
- **Several Problems on one model: install all of them before displaying any.** Installing lazily, one display at a time, is O(N²) over N problems.
- **A single deep expression is the other ceiling.** Rendering a chain of binary operators costs about 1.35x per added link, easing to 1.18x by twenty links, where one render takes roughly two minutes. Nothing caps it, so an over-deep expression reads as a hung query rather than an error — aggregate over data instead of writing a long arithmetic chain into one constraint.

Variables have no `display_string`. Query their rows directly via the DSL:

```python
# All variables of one subconcept
print(model.select(x_vars.name, x_vars.lower, x_vars.upper).to_df())

# Or sample by name
print(model.select(x_vars.name, x_vars.lower, x_vars.upper).where(x_vars.name == "flow_NYC_LAX").to_df())
```

Narrow or cap the rows with an ordinary `where`:

```python
from relationalai.semantics.std import aggregates as aggs

# One row by name (or any other property)
print(model.select(cap.name, cap.display_string).where(cap.name == "cap_NYC_LAX").to_df().to_string(index=False))

# First 10 rows in plain-text name order (cap_10 sorts before cap_2)
print(model.where(aggs.limit(10, cap.name)).select(cap.name, cap.display_string).to_df().to_string(index=False))

# Cap with aggs.limit in a where, NOT Fragment.limit -- the latter exists on the
# fragment but raises "[Feature unavailable] ... 'order_by' ..." against RAI.
```

A predicate that matches nothing returns an empty result, with no warning — read it with `.to_df()` and check `len(df)` rather than eyeballing a render.

`problem.display(limit=N)` still caps the printed whole-problem summary at its first N rows per table, applied per type section so objectives cannot crowd out constraints. The header counts stay accurate for the whole problem. `N` must be a positive integer. `limit` cannot be scoped to one part; use the selects above for that.

Plain-text ordering also applies *inside* one rendered expression: `sum` members and other bag arguments print sorted as text, so a member reading `x_10` precedes `x_2`. Bags settle one level per rendering pass and there are three passes, counting only levels whose members are not themselves plain variables, so three such levels nested inside one another can print the outermost bag's members out of order. Every member is still present and each member's own text is exact. Compare rendered constraints by their content, not by member position.

**Both forms cap by plain-text order, not numeric.** `.name` is a string, so over `cap_1`..`cap_12` both `problem.display(limit=5)` and `aggs.limit(5, cap.name)` keep `cap_1, cap_10, cap_11, cap_12, cap_2`. Either is a sample, not the numerically-first N — filter by name when you need specific rows. The `aggs.limit` form also **drops rows whose `.name` is unpopulated**: a `satisfy(...)` called without `name=` has a null name, so it vanishes from the capped read while appearing in the uncapped one. Name every constraint or objective you intend to sample this way.

To list grounded groupings without rendering the formula text — useful for very-large constraints where even a capped render is more than you need:

```python
# All grounded names (DataFrame)
grounded = model.select(cap.name).where(cap).to_df()

# Sample (filter by name)
sample = model.select(cap.name).where(cap).where(cap.name == "cap_NYC_LAX").to_df()
```

## `problem.printed_model()` — Solver Model Text Representation

After calling `problem.solve()` with `print_format=`, access the text representation via `problem.printed_model()` (Relationship) or `problem.solve_info().printed_model` (Python):

```python
# Get LP format (useful for debugging)
problem.solve("highs", print_format="lp", print_only=True)
print(problem.solve_info().printed_model)

# Available formats: "moi" (MathOptInterface human-readable), "latex", "mof" (MathOptInterface JSON), "lp", "mps", "nl" (AMPL)
```

Use `print_only=True` to inspect the formulation without actually solving. Works with or without `print_only`.
