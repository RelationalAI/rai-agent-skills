# Output Format and Feedback Loop

Read this file immediately before producing the summary after code generation.

## Summary sections

Produce one SQL file (or one Python file for RAI) saved to the working directory, plus a short summary in chat with these three sections in order. Do not embed long code blocks in chat when the artifact already contains them — link to the file instead.

### 1. Configuration

A table of confirmed configuration fields. Always use these exact field names, in this order, with no additions or renamings:

| Field | Tasks |
|---|---|
| Task type | All |
| Temporal vs non-temporal | All |
| Source entity | All |
| Target entity | Link and repeated-link only |
| Label definition | All |
| Cutoff strategy | Temporal tasks only |
| Activity filter | All |
| Splits | All |

- Never use "Label", "Entity", or any other variant — the names above are the contract.
- Omit "Target entity" entirely for non-link tasks. Do not add a row with an empty value.
- Omit "Cutoff strategy" entirely for non-temporal tasks. Do not add a row with an empty value.
- Splits: one compact row, e.g. `train ≤ 2005-10-01 / val 2006-03-01–2007-10-01 / test 2008-03-01–2009-05-01`. Never expand into three rows.

### 2. Query logic

A bulleted list giving a high-level explanation of the produced code.

**First bullet — relationships traversed**: list every join path the query takes, naming the source tables and the column used to join them. Example: "`CUSTOMERS → ORDERS` (via `customer_id`) → `PRODUCTS` (via `product_id`)"

Remaining bullets — focus on:
- What the query is doing in plain English (one sentence overview)
- How the key entities are extracted and from which source tables
- Why key operators were chosen (e.g. why LEFT JOIN instead of INNER JOIN, why MAX(CASE WHEN...) instead of COUNT)

For **temporal tasks**: end the section with one sentence noting whether any temporal leakage risk exists and how it is addressed. Example: "All feature CTEs are bounded by `<= cutoff_orders_order_ts`; only the label CTE reads forward — no leakage."

For **non-temporal tasks**: if the label is a direct function of features that will also be visible to the GNN as node or edge attributes, append a single **label-feature overlap note** at the end:

> **Label-feature overlap**: `label` is derived from `<feature(s)>`, which will also be visible to the GNN as `<edge/node>` features. The model can learn the label analytically — `<implication for this specific task>`.

Only include this note when the overlap exists. Omit it if the label comes from a source not present in the graph.

### 3. How to run

Step-by-step instructions: run Sections 1–2 to populate STAGING, run the validation queries and check the expected values, then run the final section to materialise the split tables.

**If the user opted out of SQL validation entirely in Step 0** (`GUIDED.md` only — the `one-shot` sub-skill has no opt-out branch), immediately follow the How to run section with this note, then leave two blank lines before the proactive-offer questions below:

> **Note:** As you requested, I skipped validation on this one, so it's worth a quick look before you run it. If anything comes back as an error, just paste it here and I'll fix it up.

**Else, if the EXPLAIN road did not run** (per `utils_validation.md` — no live Snowflake session was available this session), immediately follow the How to run section with this note instead, same placement:

> **Note:** This SQL was generated by an LLM. I've validated it as thoroughly as I can — syntax, schema, and structural checks all passed — but it hasn't actually been executed against Snowflake, so there's still a chance it errors when you run it. If that happens, just paste the exact error message back here and I'll fix it.

Skip this note entirely if the EXPLAIN road ran — every statement already executed successfully via `EXPLAIN` in that case, so there's nothing to caveat. Do not invent a replacement sentence either (e.g. "every statement has been validated via EXPLAIN...") — say nothing about validation at all in this case.

### Proactive offer

After the How to run section (and the note above, if applicable — shown once, in that section only; do not repeat it here), always add these two closing lines:

> Want a line-by-line walkthrough of the SQL, or would you like to discuss a specific part of the query in more detail?
>
> Is there anything in the query you'd like to change?

The note about why validation is incomplete (SQL-validation opt-out, or the EXPLAIN road not running — see "How to run" above) belongs there and only there. Nothing about it repeats here, regardless of which case applies. The one exception below (the `STAGING`-dependent EXPLAIN gap) is a separate, permanent caveat that was never meant to appear in the summary at all: **never mention it, in any form** — it's not evidence of risk in *this* SQL (it would be identical for every task table this skill ever generates), so surfacing it adds no actionable signal and only reads as an alarming caveat, especially to a non-advanced user. This applies in full even though the `STAGING`-dependent statements (the DDL and the `TRAIN`/`VAL`/`TEST` selects) couldn't be `EXPLAIN`'d standalone — see `utils_validation.md`'s EXPLAIN road for why that's a permanent, always-true property of validating a multi-statement script this way, not a per-run gap.

## Class balance check (binary and multilabel tasks)

After the summary and proactive offer, add this prompt for binary and multilabel tasks:

> To see the label distribution before materialising the split tables, please run the class balance validation query from Section 3 of the SQL and paste the result here.

When the user pastes the result, just state the positive rate plainly — e.g. "X% positive rate in training." Do not characterize it as healthy, too low, or too high, and do not suggest widening/narrowing the prediction window or adjusting the activity filter based on it. There is no universal target range for class balance — a heavily imbalanced task (e.g. 1% positive) can carry strong signal and produce a good model, so whether a given rate is a problem depends entirely on the task and is the user's call, not a fixed threshold to apply on their behalf. If the user asks whether the rate looks okay or wants advice on adjusting it, discuss it with them directly instead of applying a rule.

## Feedback loop

After the summary is delivered, the user may request changes to the SQL, or report that it failed to run. Distinguish between these kinds of changes:

**Query logic change** — the user wants to change what the query computes: a different label definition, a different join, a different filter, a different aggregation. For these:

1. Apply the change to the SQL file.
2. Regenerate the full summary (all applicable sections: configuration, query logic, how to run).
3. End with the proactive offer.

**SQL-only change** — the user wants a cosmetic or structural adjustment that does not change what the query computes: renaming a CTE, reordering columns, changing formatting, adding a comment, fixing a typo in a column alias. For these:

1. Apply the change to the SQL file.
2. Show only the changed lines as a concise diff (before → after). Do not regenerate the full summary.
3. End with the proactive offer.

If unsure whether a change is SQL-only or a query logic change, treat it as a query logic change and regenerate the full summary.

**User-edited file** — the user edits the SQL file directly and then asks for a review. For these:

1. Read the current file.
2. Identify what changed relative to the last generated or described version.
3. Review the change against these checks, flagging any failure:
   - **Syntax**: resolve `sqlfluff` per `utils_python_environment.md` (if not already resolved this session) and run `<venv>/bin/sqlfluff parse --dialect snowflake <file>` on the edited file — never a bare `sqlfluff` that might resolve elsewhere on `PATH`, and do not just eyeball it. A `PRS` violation means the SQL is no longer valid/executable (unclosed CTEs, mismatched parentheses, missing commas, or broken references between CTEs).
   - **Logic change**: describe in plain English what the edit changes about what the query computes — e.g. "the activity filter now requires at least 2 events instead of 1" or "the label window was widened from 45 to 90 days". If the edit is purely cosmetic and changes nothing about the output, say so explicitly.
   - **Schema contract**: all required columns are present with the correct names and types (entity join key, `label`/`value`/target FK, `cutoff_<table>_<source_time_col>` for temporal tasks).
   - **Temporal leakage** (temporal tasks only): all feature CTEs are still bounded by `<= cutoff`; only the label CTE reads forward.
4. Show a concise diff of what changed (before → after) and a short verdict: either "looks correct" or a specific description of what needs to be fixed.
5. End with the proactive offer.

**Execution error** — the user ran the SQL against Snowflake and pasted back the error it raised (this only comes up when the EXPLAIN road didn't run — see the "How to run" note above). For these:

1. Read the error message and identify exactly which statement and which cause it points to.
2. Apply the minimal fix that addresses that specific error. Do not rewrite unrelated parts of the query.
3. If a validation environment was set up this session (i.e. the user didn't opt out in Step 0), re-run the local-tool road validation (`utils_validation.md`) on the fixed file before responding. Otherwise, apply the fix directly without re-validating.
4. Show a concise diff of the fix (before → after) with a one-sentence explanation of what caused the error.
5. Ask the user to re-run the corrected SQL. If it errors again, repeat this loop with the new error.
6. If the same error persists after 3 fix attempts, stop looping — summarize what you've tried and ask the user for more context (e.g. the exact schema of the failing table, a fuller stack trace) rather than continuing to guess.
7. Only regenerate the full summary if the fix also changes query logic (per the query-logic-change case above); otherwise end with the proactive offer once the fix looks clean.
